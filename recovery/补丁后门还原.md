# 补丁后门还原

> **本仓库不覆盖系统补丁改造。** 本文只说明为什么"打完补丁不还原"很危险，以及收尾的正确姿势。

## 为什么"打完补丁"是一个危险习惯

越狱社区里有一种"顺手"习惯：越狱脚本运行之后，往里面注入个 `telnetd`、`dropbear`、或者 `ssh` 之类的东西留个后门，方便以后 SSH 进去折腾。

看起来省事，其实**很危险**：

- 越狱脚本**每次重启都会再跑一次**。你今天删了 debug 标记、下次重启系统一跑，后门又自动开回来。
- 一旦系统更新、hotfix 重打、或者 KOReader 触发 U 盘扫描重启，脚本再跑，后门状态就**不可预测**。
- 最坏的情况：后门脚本本身出错（比如 SSH 密钥过期、`telnetd` 崩了），系统启动挂在启动流程上，变成软砖。

**根因**：越狱脚本是**常驻执行**的，任何你加进去的东西都会**每次启动都生效**。想让后门只在某次存在、之后彻底消失，光删标记不够。

## 收尾的正确姿势：整体回写原版

给越狱脚本打补丁后，收尾必须做**整体回写**——把原版完整拷回来，而不是只删标记。步骤：

1. **先备份原版**。给越狱脚本打补丁前，先 `cp -a` 一份到别处：
   ```bash
   # 在设备上
   sudo cp -a /path/to/original /path/to/original.bak
   ```
   或从 Windows 侧把源目录里的原始文件再拷一份做备份。

2. **打补丁**。修改脚本，注入后门或临时改动。

3. **收尾时整体回写原版**：
   ```bash
   sudo rm /path/to/modified
   sudo cp -a /path/to/original.bak /path/to/modified
   ```
   不要"删除我加的几行"、"还原我改的那几行"——直接整个文件覆盖回原版。

4. **SHA256 复核**。改完之后对原版和回写后的文件各算一次哈希，必须**完全一致**：
   ```bash
   sha256sum /path/to/original.bak
   sha256sum /path/to/modified
   # 两行输出必须相同
   ```

5. **grep 确认无残留**。搜一下你注入过的关键字，确认没漏：
   ```bash
   grep -rn "telnetd\|dropbear\|ssh-server\|debug_marker" /path/to/
   # 应该无输出
   ```

## 为什么整体回写比"打标记"可靠

- **整体回写** = 文件字节级完全一致，没有"我以为还原了"的模糊地带。
- **打标记**（比如删注释、`if debug = false` 之类）依赖代码逻辑正确执行到分支。如果 debug 变量本身有残留、或分支条件写错，后门继续生效。

## 出处

社区经验（`qianjindelvdai/kindle-revive` 的 README）明确提到过这个坑，原话大意：「打完补丁要 rm + cp 原版整体回写，不能只删 debug 标记——脚本再被执行时后门照开」。
